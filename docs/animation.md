# Animation und Morph Targets

`src/scripts/animation.js`.

- Morph Targets (Blendshapes): Meshes mit `morphAttributes.position` sind immer „posed“, der Importer liefert `result.animation` auch ohne Clips (Puppe bleibt). `ModelAnimation.morphs` (Name → Meshes, gleiche Namen mehrerer Meshes = ein Regler), `setMorph`/`getMorph`/`morphValues`/`setMorphs`. Scene Graph: Modell-Zeile mit Regler-Symbol (`morphs` = Anzahl, `refreshSceneGraph`). Eigenschaften (Modell oder Bauteil mit solchen Meshes): Abschnitt „Morph Targets“ mit Regler 0–1 je Form + „Alle auf 0“ (`morphApi` in viewer.js): Ziehen = Puppe live (GPU), Loslassen = einmal einbacken (`settle({ morphsOnly })`: nur Meshes, die eine Form tatsächlich bewegt – `_morphAffected`, gecacht; 3 s → 0,3 s), ein Rückgängig-Schritt je Regler (`mergeKey`). Szenen-Zustand je Modell `morphs: { Name: Wert }` (`setModelMorphs`). Abspielleiste/Leertaste/Zeitleiste nur für Modelle mit Clips (`clipAnims()`). Szenen-Zustand je Modell `animation: { clip, time }` (`animState`/`setModelAnimation`). Morph-Normalen werden nicht eingerechnet (Datei hat keine). Live-Puppe: `mergeGroups` (animation.js) ordnet den Index der Original-Geometrie nach Material und macht eine Zeichengruppe je Material – vorher eine Zeichengruppe je FBX-Gruppe (bei zehntausenden Gruppen > 100 000 Draw-Calls je Bild → Regler zäh). Erster Live-Zug einmalig langsamer (Morph-Textur + Shader). FBX nennen Texturen oft nur per Dateiname – per `?model=` aus einem Unterordner dann nicht gefunden (Ordner ablegen geht).
- Animation (`animation.js`, animierte glTF/FBX/USD): Importer behält bei Dateien mit Clips das Loader-Objekt als „Puppe“ (`result.animation = { root, clips, scale, links }`, je Mesh-Eintrag Quell-Mesh/Instanz/posed + `sourceVertex` = eigener → Quell-Vertex). `ModelAnimation`: `AnimationMixer` auf der Puppe, je Bild `apply()`: Mesh-Matrix = Skalierung · Quell-`matrixWorld` (Knoten-Animation), verformte Meshes (Skinning/Morph): beim Abspielen/Ziehen wird das `SkinnedMesh` der Puppe selbst gezeigt (GPU-Skinning; Puppe in einem Container mit Skalierung → mm unter der Modell-Wurzel, mit unseren Materialien, unsere gebackenen Meshes so lange ausgeblendet – `startLive`/`stopLive`), erst bei Pause einmal per CPU in unsere Meshes übernommen (`getVertexPosition` + Normalen über `applyBoneTransform`). Vorher CPU-Skinning + kompletter Upload jedes Bild → stark ruckelnd. Kontaktschatten und Zeitanzeige beim Abspielen nur ~10×/s. Play/Pause-Symbol nur bei echtem Zustandswechsel setzen – das Neusetzen alle 100 ms tauschte das Element zwischen Maus-Drücken und -Loslassen → Klick auf Pause ging verloren. Live-Teile folgen Bauteil-Verschiebungen/Drehungen/Explosion (`_followParts`: X = Bewegung der Bauteil-Gruppe in Weltkoordinaten = Wurzel · (Wurzel⁻¹ · Gruppe) · Wurzel⁻¹, je Bild; überschriebenes `updateMatrixWorld` der Puppen-Meshes multipliziert X nach three.js' eigener Berechnung auf `bindMatrixInverse` (Skinning, attached: Ergebnis = matrixWorld · bindMatrixInverse · S) bzw. vor `matrixWorld` (nur Morph) – DetachedBindMode geht nicht, setzt bindMatrixInverse jedes Bild neu; geprüft: Vertex live = Vertex nach Pause, Abstand 0 bei verschobener + gedrehter Gruppe; vorher sprang das Teil beim Abspielen an die Originalposition). Laden/Hinzuladen pausiert die Animation (`stopAnimation`) – die Puppe darf dabei nicht in der Szene hängen. Puppen-Meshes können Material-Arrays haben (kein `userData`) → alle Zugriffe `material?.userData?.materialId` (vorher „Cannot read properties of undefined (reading 'materialId')“ beim Hinzuladen während der Wiedergabe). Abspielleiste `#playbar` über der unteren Leiste (nur mit Animation): Play/Pause (auch Leertaste), Zeitregler, Zeit, Clip-Auswahl bei mehreren Clips; alle animierten Modelle (auch Zusatzmodelle) teilen eine Zeitleiste (neu hinzugefügte springen auf die aktuelle Zeit – `addAnimation`; vorher Start bei 0 → versetzt; Clips unterschiedlicher Länge schleifen je für sich). Abspielen in HQ schaltet auf Default (`hqBeforePlay`), Pause schaltet zurück auf HQ; HQ während der Wiedergabe pausiert zuerst (vorher: Zoomen/Drehen weckte den Pathtracer, die Animation lief unsichtbar weiter). Beim Abspielen/Ziehen nur Raster (`pauseForEdit`), danach `settleAnimation`: Bounding-Boxen neu, `boundsTree` verworfen, bei Verformung neue Pathtracing-Szene. Picking (Hover, Material-Drag, Klick) trifft nie die Puppe (`mesh.raycast = () => {}` – `SkinnedMesh.raycast` skinnt jeden Punkt auf der CPU, Zehntel-Sekunden je Strahl → Ruckeln beim Material-Ziehen während der Wiedergabe), sondern unsere ausgeblendeten Meshes (`userData.liveHidden`, `isShown` lässt sie zu; Pose vom letzten Einbacken): 0,3 ms. `dragover` pickt nur bei geänderter Zeigerposition/Alt (`dragPick`). Clip + Zeitpunkt im Szenen-Zustand (siehe Morph Targets); Tangenten verformter Meshes bleiben vom Import.
- Erstes Abspielen ohne Hänger (Nov. 2026, Nutzer: „das abspielen einer animation (z.B. fbx) dauert beim ersten mal extrem lange bis er irgendwas initialisiert hat … erneutes abspielen ist auch kein problem“): Das erste Live-Bild einer Puppe brauchte neue Shader-Varianten (Vertex-Shader mit Knochen-Matrizen bzw. Morph-Textur, je Material, dazu der AO-Vorpass) – three.js baut sie im Bild und legt die Pipelines synchron an; der Haupt-Thread wartete in `getCurrentTexture` auf den blockierten GPU-Prozess (FBX-Figur mit 5 Maps: ein Bild 1,1 s, CPU-Profil: 1,17 s in `getCurrentTexture`, Node-Bau klein). Jetzt `goLive(anim)` in viewer.js statt `anim.startLive()` an allen Stellen (Abspielen, Zeitleiste, Gelenk-Zug, Posen-Überblendung, Morph-Regler): mit neuen Materialien / anderem Modus / Linsen-Ziel (`liveCompileKey`: `anim.liveKey()` = Material-ids der Puppe + Modus, HQ zählt als Default, + Linsen-Ziel) kompiliert das nächste Bild nur – `compileLive`: `compileAsync` nur des Puppen-Containers mit den Lichtern der Szene (`shader-compile.js`, Parameter `targetScene`), ins Linsen-Ziel wenn aktiv, dazu `rasterAO.compile` für den AO-Vorpass; Pipelines asynchron. Dafür der Ablauf des ersten Basic/Default (`prepare`, docs/rendering.md): bis fertig wird nicht gezeichnet (Bild bleibt, Status „Übernehme Szene“, Seite bedienbar), Animationsuhr und Posen-Überblendung warten (`preparing()` in `stepAnimation`/`stepPoseBlend`). Zusätzlich `precompileLive` nach dem Laden im Leerlauf (`addAnimation` → `whenIdle`, wartet auf Laden/andere Kompilierung): die Puppe hängt nur während three.js sie einsammelt (synchron im Aufruf) in der Szene (`startLive` … `stopLive` ohne Bild dazwischen) – so startet schon das erste Abspielen sofort; drückt man vorher auf Play, wartet `goLive` auf den laufenden Auftrag (`anim.compiling`). Nur für Modelle mit Clips: mit Morph-Targets baut das Kompilieren three's Morph-Textur in einem synchronen Schritt (Kopf mit 7 Formen: 0,8 s + 3 × 0,15 s Hänger direkt nach dem Laden) – ein reines Morph-Modell zahlt das erst beim ersten Regler-Zug. Gemessen (RTX 3080, Windows-Chrome; Hänger = lange Aufgaben/rAF-Lücken): FBX-Figur warm alt 1,1 s → neu keiner (Start nach 22–93 ms), kalter Shader-Cache alt 2 × 0,22 s → neu keiner, Play direkt nach dem Laden neu 0,3–0,5 s bis Start ohne Hänger; zweite FBX kalt alt 0,71 + 0,32 s → neu keiner; animierte glTF-Szene kalt alt 0,76 s → neu 94 ms; erster Morph-Regler-Zug alt 2 × ~1 s → neu 0,75 s (Morph-Textur) + 0,15 s, erstes Bild nach 1,2 s. Schatten-Varianten kompiliert `compileAsync` nicht – im ersten Live-Bild ohne messbaren Hänger. Prüfskripte Scratchpad `anim/` (`play1.js` erstes/zweites Abspielen, `scrub1.js` Zeitleiste direkt nach dem Laden, `morph1.js` erster Regler-Zug, `idle1.js` Hänger nach dem Laden, `cold.sh` frisches Chrome-Profil = kalter Shader-Cache; alter Stand über `dist/old/`).
- Spezial-Materialien beim Abspielen (Okt. 2026, Wunsch des Nutzers): Puppen-Meshes tragen `userData.animationPuppet` – Gras, Wolle und Wolke (`grass.js`, `wool.js`, `clouds.js`) lassen sie bei der Suche aus (sie folgen unseren Meshes). Live sind unsere verformten Meshes ausgeblendet → Gras-Halme aus, die Puppe zeigt die dunkle Gras-Grundfläche; Wolle: nur die Grundfläche (passt laut Nutzer). Wolke: die Puppe bekommt statt des unsichtbaren Wolken-Materials ein schlichtes Material in der Grundfarbe (`_liveMaterial`, je Wolken-Material eines, mit `dispose`) – vorher verschwand das Modell beim Abspielen ganz. Nach der Pause: `settleAnimation` → `grass.invalidate()`; der Gras-Schlüssel enthält `position.version` (die Pose) – neue Pose = alte Halme sofort weg (kein Überblenden, sonst stand das alte Gras kurz auf der neuen Form), neue wachsen mit Fortschrittsanzeige und blenden ein. Geprüft: animiertes glTF, 10 Meshes, Wiese → nach Pause in ~2 s neu, keine Fehler (Scratchpad `ganim.js`).
- Skelett (Okt. 2026, Wunsch des Nutzers: „gleich die SkeletonHelper einbauen, damit das Skeleton auch so bewegt werden kann“): `src/scripts/skeleton-view.js`. Modelle mit Hautgittern bekommen eine Puppe auch ohne Clips und Morphs (`mesh-importer.js`: `isSkinnedMesh` reicht). Eigenschaften des Modells, Abschnitt „Skelett“: „Anzeigen“ (oder Klick auf das Skelett-Symbol der Modell-Zeile im Scene Graph – `skeleton.svg`, Strichfigur mit Gelenkpunkten, Wunsch des Nutzers „damit man direkt sieht, ob ein Objekt ein Biped hat“; Tooltip mit Gelenkzahl, blau solange angezeigt; `content.bones`/`skeletonShown` aus `refreshSceneGraph`) blendet Knochen (Linien zum Eltern-Knochen) und Gelenke (Punkte, feste Bildschirmgröße) über allem ein – eigene Objekte in der Overlay-Szene des Gizmos statt three's `SkeletonHelper` (der rechnet im Raum der Puppe, die ohne Abspielen nicht in der Szene hängt: `ModelAnimation.sceneMatrix` = live `matrixWorld`, sonst Modell-Wurzel · `matrixWorld`, `updatePuppetMatrices` hält die abgehängte Puppe aktuell). Klick auf ein Gelenk (Abstand ≤ 10 px auf dem Bildschirm, das vorderste; vor der normalen Auswahl) wählt es: eigenes TransformControls (drehen in lokalen Achsen, E; verschieben, W – auch über das Quad-Menü, Rechtsklick auf einen Gelenkpunkt wählt ihn; Esc/Klick daneben hebt auf), das Modell-Gizmo wird solange abgehängt. Das Gizmo bewegt einen Griff an Position + Drehung des Gelenks (ohne Skalierung), daraus die lokale Transformation des Knochens (Eltern-Szenenmatrix⁻¹ · neue Lage, Skalierung bleibt). Ziehen = Puppe live (GPU-Skinning, `startLive`, Pathtracer pausiert), Loslassen = Pose eingebacken (`settleAnimation`), ein Rückgängig-Schritt je Zug; läuft die Animation, hält sie beim Ziehen an. Szenen-Zustand je Modell `pose: { Knochenname: [px,py,pz,qx,qy,qz,qw] }` (nur Knochen abseits der Importpose, gleiche Namen `name~k`; leeres Objekt = Importpose; nach Clip + Zeit angewendet; ältere Szenen ohne `pose` bleiben, wie sie sind). „Pose zurücksetzen“ (nur nach Posieren von Hand – `handPosed`, bei Modellen mit Clip weicht die Clip-Pose ohnehin ab): alle Knochen zur Importpose, mit Clip danach die Clip-Pose der aktuellen Zeit. Der Clip überschreibt beim Abspielen/Ziehen der Zeitleiste die Knochen, die er animiert; die übrigen behalten die Handpose. **Posen-Liste** (Okt. 2026, Wunsch des Nutzers „wie wähle ich andere, fertige Posen aus?“): im Abschnitt „Skelett“ die Posen der Datei (USD: SkelAnimations ohne Zeitwerte, docs/mesh-import.md – teilweise angewendet: nur ihre Knochen) und eigene Posen; Klick = anwenden (ein Rückgängig-Schritt, zurück zur Haltung davor; Nutzer: „können wir zwischen den Posen blenden?“ → weich überblendet, `blendPose` in viewer.js: Positionen linear, Drehungen per Slerp, Smoothstep über `SKELETON.poseBlendMs` in config.js (450 ms, 0 = springen), Puppe live, am Ende die exakte Pose eingebacken; gilt auch für Rückgängig/Wiederholen und „Pose zurücksetzen“ – mit Clip zur Clip-Pose der aktuellen Zeit; Zeit je Bild gezählt, höchstens 50 ms: das erste Live-Bild kompilierte die Skinning-Shader und blockierte – nach Wanduhr war die Überblendung dann schon halb vorbei (seit Nov. 2026 wartet sie, solange `goLive` kompiliert); Abspielen, Zeitleiste, Gelenk-Zug oder Modellwechsel beenden eine laufende Überblendung sofort am Ziel; geprüft Scratchpad `blend.js`: Bein 0° → 43,5° in ~450 ms gleichmäßig, Ende exakt), die zuletzt angewendete ist markiert, bis sich etwas bewegt (`activePose`, gelöscht von Gelenk-Zug, Zeitleiste, Abspielen). „Pose speichern“ nimmt die aktuelle Haltung (auch einen Clip-Zeitpunkt) als „Pose n“ auf und öffnet gleich das Umbenennen (Enter/Verlassen übernimmt, Esc bricht ab); eigene Posen: Stift = umbenennen, × = löschen – alles mit Rückgängig. Werte im Speicher und für Rückgängig ungerundet (`poseValues({ round: false })` – gerundet wich das Zurück messbar ab), im Szenen-Zustand je Modell `poses: [{ name, values }]` auf 7 Stellen. Geprüft (Scratchpad `poses.js`, Testdatei mit drei festen Posen, eine gebunden): Liste, Anwenden, Rückgängig exakt, Speichern/Umbenennen/Löschen, Szenen-Zustand stellt eine gelöschte eigene Pose wieder her. Grenzen: Live-Teile folgen Bauteil-Verschiebungen (`_followParts`), die Knochen-Anzeige nicht; zwei Figuren mit gleichen Knochennamen: der Mixer findet nur die erste. Geprüft (Scratchpad `skel.js`: anzeigen, echter Klick aufs Gelenk, Gizmo-Ereignisse nachgestellt, Einbacken, Szenen-Zustand, Rückgängig exakt zurück): USD-Figur (66 Gelenke), glTF mit Clip (147), FBX mit Morphs (52).
